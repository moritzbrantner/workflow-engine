# Workflow Engine technical decisions

Technical implementation choices for Workflow Engine. Product behavior remains governed by the owning [Workflow Editor Decision Atlas](https://github.com/moritzbrantner/workflow-editor/blob/main/docs/DECISION-ATLAS.md); this document does not authorize new product features.

### TECH-001 — Persist a continuation checkpoint at human-interaction waits

- **Status:** owner-approved 2026-10-17, /tech-steer choice **A**.
- **Product basis:** [Workflow Editor Atlas 5.16](https://github.com/moritzbrantner/workflow-editor/blob/main/docs/DECISION-ATLAS.md) (approval/rejection and typed human input); [Workflow Engine #19](https://github.com/moritzbrantner/workflow-engine/issues/19) and [Workflow Editor #105](https://github.com/moritzbrantner/workflow-editor/issues/105).
- **Context:** The engine already pins compiled workflow identity and stores JSON-safe run records behind `WorkflowEngineStore`, but the current dispatcher and run state have no waiting/continuation contract. A human wait must survive a single-host restart without holding the runner open or repeating completed external operations.
- **Selected approach:** On reaching an authored human-interaction Node, the runner returns a **structured suspension/continuation checkpoint** through the existing dispatcher boundary. The engine atomically persists that checkpoint with a `waiting` run and pending task using the existing store. The checkpoint identifies the original run and immutable compiled workflow version/digest, waiting Node/task and typed response boundary, completed work and reusable output provenance, and the remaining execution position; retain relevant already-consumed execution bounds. Persist only JSON-safe values and verified artifact references, never live streams, secrets or raw binary.
- **Resume:** The host verifies who may answer; the engine validates the response against the compiled contract, atomically claims the pending task, and dispatches the **same run** from the checkpoint. The runner resumes unfinished work without replaying completed side-effecting Nodes. Preserve the existing run ID, workflow binding and idempotency identity; distinguish approve, reject and supplied/corrected typed values. A duplicate response or concurrent restart must not dispatch a second continuation. Treat uncertain dispatch delivery conservatively as today, not as proof of safe replay.
- **Ownership:** Workflow Engine owns durable waiting state, checkpoint storage, response coordination and resume dispatch. Workflow Runner owns checkpoint capture/validation and execution resumption. Workflow Editor owns typed human-task authoring and connected task UI. Reuse the existing `WorkflowEngineStore`/file-store conformance and `WorkflowRunDispatcher`; do not add an event-sourcing system, second scheduler, approval backend or runner implementation. Extend the versioned handoff and state transitions explicitly; preserve existing compiled-v1 and ordinary-run behavior.
- **Alternative:** Reconstructing continuation from execution-event history (**B**) would require an event-replay authority and stronger deterministic replay/effect contracts without adding value to this first single-host pause/resume slice. Not selected.
- **Evidence required:** Engine #19 and Editor #105 need a real approval/rejection and typed-input journey, durable restart-and-resume, exactly one continuation claim, unchanged run identity, rejected stale/duplicate responses, no duplicate completed external side effects, and unchanged ordinary runs. These are **unimplemented acceptance requirements**, not verified results.
